# Ary Nexus Roadmap

## Current Snapshot

**Canonical status and work-order document. Audited September 7, 2026.** Read this file before interpreting an old feature prompt. Inspect the relevant current implementation again before editing it. Historical `*_TEST_REPORT.md` files are evidence records, not competing roadmaps; their old “next milestone” recommendations are superseded by this file.

- **Architecture:** Next.js UI → existing catch-all HTTP API → domain/services → typed Repository → Supabase/PostgreSQL. `AryBrainService` composes existing intent/entity/retrieval/reasoning/extraction services. External and internal tools use `ToolRegistry` → `ActionRequestService` → `ActionService`/`PermissionService`.
- **Stack:** Next.js 16.3.4, React 19, TypeScript, PostgreSQL/Supabase, pgvector, Zod; Electron 44.2.0 desktop development launcher; vgpu 0.4.0 visual effects; MediaPipe hand detection. No installed xyflow, Three.js, GSAP, Rive or separate agent-framework runtime. Reference repositories are reference material, not merged applications.
- **Active configuration:** local `ARY_STORAGE=supabase`, reasoning/embeddings `openai`; defaults are Responses API `gpt-5.6-sol` and `text-embedding-3-large` at **384 dimensions**, version `openai-te3-large-384-content-summary-v1`. OpenAI and Supabase credentials are present; values were not printed or copied. Mock/local/compatible providers remain explicit alternatives. Speech defaults are `gpt-4o-mini-transcribe` and `gpt-4o-mini-tts`; live access is not proven by configuration.
- **Storage:** owner-scoped Postgres tables/RLS, vector/full-text RPCs, version/evidence tables, leased jobs and transactional batch RPC. `LocalRepository` is an explicit localhost-only development store, disabled in production. Google tokens/operation guards use a shared encrypted **single-host file vault**, not a second memory store.
- **Working foundations:** persistent memory/conversations, canonical identity/aliases, hybrid retrieval, reviewed temporal facts, graph query/rendering, actions/approvals/audit/idempotency, real task/project actions, Priority, advisory Board, base ROI, Finance statement visibility and spatial navigation. Live completion gaps are listed separately below.
- **Current verification:** fresh audit run: **577 automated tests passed across 42 files**, TypeScript passed, configured Prettier check passed, production `next build` passed. No separate lint script is configured. The preceding Finance verification also passed 14 fixture browser checks and 8 real browser/HTTP/local-persistence checks. Those are isolated tests, not bank/provider production certification.
- **Visual system:** CSS 3D orbital shell, shared spring/camera sequence, glass cards, blue/white/violet atmosphere, hideable HUD, classic/2D fallback. Brain interaction is **Canvas2D**, with vgpu as an optional GPU enhancement. Existing workspace screens retain some original light styling alongside scoped dark Finance/Economics/Board panels. The newer center/left/right/lower-console holographic layout is not implemented as a unified workspace.
- **Permissions:** levels 0–5, user/workspace/tool/action/product scoping, most-restrictive matching policy wins, exact-request approvals, audited retries and immutable history. Workspace currently means the existing `ary-nexus` scope, not a completed multi-workspace organization system. Calendar/Gmail writes and Finance imports retain mandatory approval ceilings even at level 5.

**Read-only live audit:** the ARY NEXUS Supabase project has a valid unique `actions_execution_key` index, `memory_sources`, and `finance_snapshots` with **0 statements**. Economics migration 011's `additional_compute_cost_usd` and `tool_cost_usd` columns are **both absent**. There is **1 failed extraction job**, **0 expired running extraction leases**, and **0 failed reflection jobs**. No record, policy or migration was changed during this audit. The SQL editor has no app-user JWT: `action_execution_ready_v1()` correctly returns false in that context; direct catalog inspection confirmed the index, so that result is not an index failure.

Google Calendar client ID/secret and Gmail client ID/secret/redirect remain absent locally; the shared vault encryption key is present. The Mac being locked in earlier reports is historical, not the current explanation for incomplete setup. No new model calls, mailbox access, camera recording or external actions were performed for this roadmap.

The audit covered root structure, all 12 migration files, service entry points/core flows, API/UI wiring, provider configuration, real/mock registrations, desktop boundaries, graph/spatial/voice code, the test inventory and milestone reports. This is a repository/status audit, not a penetration-test certification or a full live migration checksum comparison.

## LATER

- Independent scheduled job/Board operation and proactive follow-up: reuse existing jobs, idempotency, shared evidence and cost controls; require restart/recovery and owner scheduling policy first.
- Multi-host/public production deployment: managed encrypted vault/locking, database-side aggregates, distributed usage limits, retention/export/deletion policy, stronger security/load testing and deployment automation. Local functionality is not proof of readiness.
- Notarized standalone desktop releases and signed remote updates: preserve exact-origin/process ownership; separate from the current source-live development launcher.
- Broader shared-workspace/commercial multi-tenant onboarding, billing and organization roles: keep existing owner isolation until membership/authorization/migration semantics are explicitly designed.
- Read-only Drive/document integration and additional third-party product adapters: require a demonstrated source need, existing approval/audit gates and selective memory evidence.
- Real `create_note`, generic message-draft or project-summary tools only when a concrete workflow requires them. Existing `mock.*` variants are simulated; reuse current memory/project services instead of adding stores.
- Investing analytics, historical market sources and **Kronos**: only after real Finance coverage/provenance is stable and explicit read-only interfaces/evaluation criteria exist. No claim of forecasting accuracy.
- Advanced financial execution/autonomous trading: not an authorized product commitment; requires a separate threat/risk model, explicit owner scope, approvals, reconciliation and recovery controls. None is supplied by Finance v1.
- Desktop bridge, allowlisted app operations, multi-display control: separate security-reviewed local capability; no generic shell, shutdown/restart or file deletion. The current desktop launcher is not this bridge.
- Native mobile/iPhone client: stable authenticated APIs, secure credential/session design and accessible non-spatial interactions first.
- Two-hand gestures, XR/multi-environment worlds and richer 3D: require measured benefit and real-device reliability; preserve static/2D mode.

## ARCHITECTURE GUARDRAILS

1. Audit before modifying: read this roadmap, current files, migrations and tests; distinguish code, configured access and live acceptance.
2. Never duplicate an existing system. Old prompts are not a missing-feature inventory.
3. Prefer additive changes with the smallest reviewed scope.
4. Preserve stable interfaces and canonical IDs. Document and test necessary compatibility changes.
5. Use existing source-of-truth services/repositories, not direct UI/provider shortcuts.
6. Do not introduce a second memory system. Agents, voice and integrations share central evidence and conversations.
7. Do not introduce a second permissions system. Work within `PermissionService` and current owner/product/workspace semantics.
8. Do not bypass approval/action logging, exact-request validation or outcome capture.
9. External tools must use the existing ToolRegistry/action pipeline and provider boundaries.
10. High-risk actions require explicit permission and approval; mandatory ceilings survive level 5.
11. Run tests/typecheck/build after each implementation milestone, plus configured formatting and realistic end-to-end verification.
12. Do not refactor unrelated code during feature work. Potential dead code is an audit finding, not permission to delete it.
13. Update **this roadmap** after every completed milestone: status, evidence/date, remaining gaps and ordering. Do not create parallel roadmap files.
14. Separate “implemented,” “verified with fixtures,” “verified with real providers” and “deployed.” Passing a mocked Google flow does not mean Google is connected.
15. Keep references as examples/packages behind Ary-owned interfaces. No wholesale Mem0/Graphiti/LangGraph/XYFlow/LiveKit application copy.
16. Distinguish atomic database transactions from external success/local receipt recovery. Preserve uncertain operation guards; never blindly resend or repeat a side effect.
17. Missing information stays unknown. No fabricated memory, financial effect, account balance, provider success or synthetic-data claim in the real workspace.

## DESIGN GUARDRAILS

Ary Nexus should feel like a **spatial operating system**: cinematic, premium, calm, intelligent, holographic, dark, restrained and high-performance. Preserve the current spatial hierarchy, readable glass/holographic surfaces, blue/white/violet lighting, isolated warning orange, smooth spring-based motion, reduced-motion support and graceful fallback.

Reuse `components/spatial/motion.ts`, the shared camera/focus lifecycle, scoped CSS variables and current graph effects before adding a motion library. Use visible states to communicate actual selection, evidence, approval, execution or failure. Number transitions must not obscure exact financial values. Ambient effects must remain subordinate to content; idle navigation settles.

Avoid generic SaaS card grids as the defining experience, cyberpunk clutter, excessive neon, constant idle motion, unreadable transparency, unnecessary 3D and decoration without informational purpose. Existing functional screens must remain usable during visual integration. The new unified hero layout is planned, not retroactively DONE. Native keyboard/HTML alternatives must remain available when Canvas/WebGPU, camera or motion is unavailable.

## SECURITY GUARDRAILS

- Apply least privilege to user/tool/action/product and provider scopes; distinguish service permissions from database owner isolation. Owner RLS alone is not an agent capability policy.
- If/when a local bridge is enabled, bind it to loopback, verify exact origin and owning process/session, and expose only explicit verbs with validated structured inputs.
- Enforce same-origin mutation rules, authentication and ownership; retain OAuth one-use state/browser binding. Review non-browser/no-Origin behavior before public deployment.
- Accept no caller-supplied shell commands. Prefer `execFile`/argument arrays over `exec`; the existing server launcher uses fixed `spawn` arguments without a shell. Never interpolate user/model text into commands.
- No shutdown/restart/file deletion capability, autonomous money movement/trading or silent high-risk external actions.
- Keep full action/approval/outcome history and source attribution, with documented access/retention. Do not equate “not in semantic memory” with “not stored.”
- Preserve idempotency, optimistic concurrency and rollback/recovery where applicable. Uncertain external outcomes require verification, not an automatic retry that repeats the effect.
- Keys remain in environment/managed secret storage; never hardcode, log or copy them into UI/test artifacts. Local encrypted vault is single-host only; credentials must not enter general repositories or prompts.
- Email/document/provider content is untrusted evidence, never instructions authorizing tools, recipients, approvals or fact supersession.
- Before internet-facing/multi-host operation, add demonstrated usage/abuse limits, retention/restore procedures, managed vault/locking, security-header review and adversarial tenant/permission tests. These are rollout prerequisites, not claims of a discovered exploit.

3. `npm run typecheck`.
